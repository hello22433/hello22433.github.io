# 발행 계획 — 애드센스 승인과 검색 유입까지

수익의 8할은 글에서 나온다. 광고 세팅은 30분이면 끝나지만, 검색 유입은 글이 쌓여야 생긴다.
아래는 지금 있는 글 3편에서 자연스럽게 뻗어나가는 **20편 계획**이다. 주 2편이면 10주, 주 1편이면 20주다.

목표: **20편 · 3개월** → 애드센스 신청 → 색인·순위 안정화(추가 3개월) → 월 1만 PV.

---

## 왜 이 주제들인가

지금 쓴 글은 세 편 모두 "실무에서 부딪힌 동시성 문제"에 걸쳐 있다.
이 영역은 검색 수요가 꾸준하고(면접·장애 대응·구현 중 검색), 경쟁 글은 대부분 번역투 요약이라
**직접 겪은 사례 + 실행 가능한 SQL/코드**를 담은 글이 상위로 올라가기 쉽다.

한 편씩 흩어진 글보다 **시리즈**가 유리하다. 내부 링크가 생기고, 한 글이 뜨면 나머지가 같이 끌려 올라간다.

## 시리즈 A — 동시성 제어 (기존 글 3편의 직계)

| # | 제목(안) | 노리는 검색어 | 핵심 |
| --- | --- | --- | --- |
| 1 | JPA `@Version` 낙관적 락, `OptimisticLockException` 이 터지는 순간 | `OptimisticLockException`, `JPA 낙관적 락` | 예외 발생 조건, 재시도 코드, 재시도해도 되는 경우/안 되는 경우 |
| 2 | 비관적 락 `SELECT FOR UPDATE`, 걸어보고 알게 된 것 | `SELECT FOR UPDATE`, `비관적 락 데드락` | 락 대기·타임아웃, 인덱스 없을 때 락 범위가 넓어지는 문제 |
| 3 | 분산 락이 필요한 순간과 필요 없는 순간 | `분산 락 Redis`, `Redisson 분산 락` | DB CAS 로 충분한 경우 vs 락이 필요한 경우 판단 기준 |
| 4 | 배치 작업을 여러 서버로 늘릴 때 생긴 문제들 | `배치 중복 실행 방지`, `스케줄러 다중 서버` | 메모리 플래그 → DB CAS 전환기 (실제 경험, 가장 유입 좋을 글) |
| 5 | PROCESSING 상태로 멈춘 작업을 되살리는 회수 로직 | `배치 작업 stuck`, `타임아웃 복구` | `claimed_at` 기반 회수, 재처리 안전성(멱등성) |
| 6 | 멱등성 없는 재시도가 만드는 중복 결제 | `멱등성 키`, `중복 요청 방지` | 멱등키 설계, UNIQUE 제약으로 막기 |
| 7 | 트랜잭션 격리 수준을 직접 재현해봤다 | `READ COMMITTED REPEATABLE READ 차이`, `팬텀 리드` | 두 세션 띄워 SQL 로 직접 재현하는 실습 |

## 글 하나를 쓸 때 지킬 것

- [ ] **제목에 검색어를 넣는다.** "낙관적 락은 락이 아니다"처럼 좋은 제목이라도, 본문 소제목에는 `JPA @Version`, `OptimisticLockException` 같은 실제 검색 표현을 함께 넣는다.
- [ ] **`description` 을 쓴다.** 검색 결과 요약문이 되고 클릭률이 달라진다. (기존 3편에는 이미 넣어 두었다.)
- [ ] **첫 문단에 결론을 적는다.** 이탈률이 곧 순위다.
- [ ] **실행 가능한 코드/SQL 을 최소 하나 넣는다.** 복붙되는 글이 링크를 받는다.
- [ ] **관련 글로 내부 링크를 건다.** 시리즈 글끼리 서로 걸면 색인과 체류 시간이 같이 오른다.
- [ ] **한 글에 문제 하나.** 섞으면 어떤 검색어로도 상위에 못 간다.
- [ ] 발행 후 **Search Console 에서 URL 검사 → 색인 요청** (초기에는 이걸 해야 며칠 안에 잡힌다).
