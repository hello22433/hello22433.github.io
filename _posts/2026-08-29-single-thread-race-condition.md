우리는 보통 싱글스레드에서는 레이스 컨디션이 일어나지 않는다고 생각하기 쉽다.
하지만 틀린 생각이다. 동시성 문제는 스레드의 문제가 주요한 관점이 아니라,
읽기와 쓰기 사이에 틈이 존재할 수 있는지이다. await 등으로 제어권을 넘기면
고치기 전에 다른 작업이 이전 값을 읽고 수정까지 가버리는 틈이 존재할 수 있다.

## 틈이 만드는 일

잔액이 10,000원인 유저에게 두 건의 차감이 동시에 일어난다고 하자.

```
A: 잔액 읽음 (10,000)
A: await ...              ← 제어권을 넘김
     B: 잔액 읽음 (10,000)  ← A가 아직 저장 전이라 같은 값을 봄
     B: 9,000 저장
A: 복귀 → 자기가 계산한 9,000 저장
```

두 번 차감했는데 1,000원만 빠졌다. read와 modify 사이의 틈에서
B의 작업이 통째로 사라진 것이다.

그렇다고 await 없이 작업할 수는 없다. DB 접근 자체가 비동기이기 때문이다.

## 해법

원자적으로 처리하면 된다.

```sql
UPDATE users SET amount = amount - 1000 WHERE id = 1
```

읽어와서 계산하는 대신 DB에서 직접 빼면 읽기 단계가 없으므로 틈도 없다.

조건을 걸어도 된다.

```sql
UPDATE tasks SET status = 1 WHERE id = 1 AND status = 0
```

이것도 하나의 CAS라고 볼 수 있다. 비교하고(where) 바꾸는(set) 작업이기
때문이다. 단, 변경된 행 수를 확인해야 한다. 0건이면 이미 다른 쪽이
가져간 것인데, 확인하지 않으면 실패했는데도 작업을 계속 진행하게 된다.

## 락으로 해결하기

계산이 복잡해 애플리케이션에서 처리해야 한다면 락이 필요하다.
[전 글에서 다룬](/posts/optimistic-lock-is-not-a-lock/) 비관적 락과 낙관적 락이 여기서 등장한다.

비관적 락은 이 틈 자체에 끼어들 수 없게 해당 데이터를 틀어막는 메커니즘이고,
낙관적 락은 동시에 작업할 수 있게끔 열어주되 해당 데이터가 바뀌었다면
수정이 되지 않게 하는 메커니즘이다.
