# 낙관적 락은 락이 아니다

배치로 대기 중인 작업을 처리하는 업무를 하고 있다. 서버 한 대로 운영하다
여러 대로 늘리는 과정에서, 현재 쓰는 메모리 플래그로는 동시성 제어가
안 된다는 걸 알게 됐다. 비관적 락과 낙관적 락을 찾아보다가,
낙관적 락은 알고 보니 락이 아니었다.

## 낙관적 락은 락이 아니다

보통 락의 종류라고 하면 두 가지를 떠올린다. 비관적 락과 낙관적 락.
하지만 엄밀히 말하면 낙관적 락은 락이라고 할 수 없다. 락이라고 하면 해당
데이터에 대한 접근 자체를 막는다는 뜻이나, 낙관적 락은 접근 자체는 허용하기
때문이다. 데이터가 틀릴 수도 있다는 것을 가정하고 접근하여, 틀린 경우에는
수정을 하지 않게끔 하는 방식이다.

## version을 사용하는 방식

흔히 알고 있는 version을 사용하여 조건부 update를 하는 방식이 그것인데,
단순히 숫자의 increment로 구현하는 방법이 대표적이다.

```sql
UPDATE orders SET amount = 5000, version = 2
WHERE id = 1 AND version = 1
```

조회 시점의 version이 1이었는데 그 사이 다른 트랜잭션이 먼저 수정했다면
version은 이미 2가 되어 있고, 위 쿼리는 0건 변경으로 끝난다.
JPA에서는 `@Version` 필드 하나만 선언하면 이 과정이 자동으로 처리된다.

## 상태값으로도 같은 걸 할 수 있다

내 경우에는 별도의 version 없이 상태값만으로 해결할 수 있었다.

```sql
UPDATE tasks SET status = 'PROCESSING', claimed_at = NOW()
WHERE id = 1 AND status = 'WAIT' AND claimed_at IS NULL
```

`status = 'WAIT'`이 비교(compare), `SET`이 교체(swap)에 해당한다.
상태 조건만으로도 동작하지만 `claimed_at IS NULL`을 함께 두면 의도가
명확해지고, 다른 경로에서 상태값만 되돌려놔 데이터가 어긋난 경우도 걸러낸다.
단, `claimed_at = NULL`이 아니라 `IS NULL`이어야 한다.
SQL에서 NULL은 `=`로 비교되지 않는다.

`claimed_at`은 조건 겸 기록용이다. 선점한 서버가 처리 도중 죽으면
PROCESSING 상태로 남는데, 일정 시간이 지난 건을 다시 WAIT으로 되돌리는
회수 로직에서 이 값을 쓴다.

## 변경된 행 수를 반드시 확인해야 한다

이 방식의 핵심은 결과 확인이다. 1이면 내가 선점한 것이고 0이면 이미
다른 서버가 가져간 것인데, 확인하지 않으면 선점에 실패했는데도
작업을 계속 진행하게 된다.

메모리 플래그와 달리 DB가 판정하므로, 서버를 몇 대로 늘리든 동작한다.

## 그런데 왜 "락"이라고 부르나

용어의 관성으로 보인다. 영어권에서도 optimistic lock보다
optimistic concurrency control이라는 표현을 쓰는 경우가 많다.
