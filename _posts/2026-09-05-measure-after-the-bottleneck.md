토이 프로젝트 README에 "바이너리 직렬화로 패킷 크기 52% 절감"이라고 써뒀다.
측정해서 나온 숫자였고, 다시 재봐도 맞았다. 50.8%.

그런데 실제로 네트워크로 나가는 건 12.7%만 줄어 있었다.

숫자가 틀린 게 아니라, **재는 위치가 틀렸다.**

## 무엇을 만들었나

WebSocket으로 게임 액션을 주고받는 서버다. 매 요청마다 JSON으로
`{"playerId":"...","action":"BET","amount":10000}`을 보내는데, `"playerId"`
같은 키가 매번 반복된다. 그래서 ByteBuffer로 직접 찍는 포맷을 만들었다.

```
[action 1byte][amount 8byte][idLen 4byte][id Nbyte]
```

측정 코드도 짰다.

```java
byte[] jsonBytes = objectMapper.writeValueAsBytes(request);
byte[] binaryBytes = BinarySerializer.serialize(request);
System.out.println("JSON: " + jsonBytes.length);
System.out.println("Binary: " + binaryBytes.length);
```

63바이트가 31바이트가 됐다. 50.8% 절감. README에 적었다.

## 첫 번째 문제: 한 점을 곡선이라고 불렀다

테스트 데이터의 playerId는 `"User_Economic_King"`, 18자였다.
길이를 바꿔가며 다시 재봤다.

| playerId 길이 | JSON | Binary | 절감률 |
|---:|---:|---:|---:|
| 4자 | 49 B | 17 B | 65.3% |
| 18자 | 63 B | 31 B | **50.8%** |
| 32자 | 77 B | 45 B | 41.6% |
| 64자 | 109 B | 77 B | 29.4% |

바이너리 포맷의 고정 오버헤드는 13바이트, JSON의 키 오버헤드는 약 45바이트로
둘 다 상수다. id가 길어질수록 분모만 커지니 절감률은 단조 감소한다.

52%는 시스템의 속성이 아니라 **입력 하나에 대한 값**이었다.
그걸 시스템의 속성인 것처럼 적었다.

## 두 번째 문제: 병목 앞에서 쟀다

이게 진짜였다.

서버는 SockJS를 쓰고 있었다.

```java
registry.addEndpoint("/ws-holdem")
        .setAllowedOriginPatterns("*")
        .withSockJS();
```

**SockJS는 바이너리 프레임을 지원하지 않는다.** 그래서 클라이언트 코드가
이렇게 되어 있었다.

```javascript
// stompClient.send(dest, headers, new Uint8Array(buffer));  // 안 됨
var base64Str = btoa(String.fromCharCode(...new Uint8Array(buffer)));
stompClient.send(dest, headers, JSON.stringify({data: base64Str}));
```

주석 처리된 줄이 내가 처음 시도했던 코드다. 안 되니까 Base64로 감싸서
JSON에 담아 보내도록 우회했다. 그리고 그 우회가 최적화를 대부분 되돌린다는 걸
생각하지 않았다.

Base64는 3바이트를 4글자로 만든다. 31바이트가 44글자가 되고,
`{"data":"..."}` 껍데기가 11바이트를 더한다.

| 단계 | 크기 | JSON 대비 |
|---|---:|---:|
| JSON 원본 | 63 B | — |
| 바이너리 직렬화 결과 ← **내가 잰 지점** | 31 B | −50.8% |
| Base64 + JSON ← **실제로 나가는 것** | 55 B | **−12.7%** |

아낀 32바이트 중 24바이트를 전송 계층에서 도로 잃고 있었다.

측정 코드는 정직했다. 직렬화 함수의 리턴값을 정확히 쟀다.
다만 그 함수 뒤에 24바이트를 다시 붙이는 단계가 있다는 걸 몰랐다.

## 세 번째 문제: 기준선이 틀렸다

여기서 결론이 뒤집혔다.

실무 WebSocket은 대개 `permessage-deflate`를 켠다. 압축을 끈 JSON을
기준선으로 삼고 있었다는 뜻이다.

메시지 100개를 연속으로 보내며 압축 컨텍스트가 유지될 때 다시 쟀다.

| 방식 | 100개 합계 | 압축 JSON 대비 |
|---|---:|---:|
| JSON 원본 | 5,190 B | — |
| **JSON + deflate** | **526 B** | 기준선 |
| 바이너리 raw | 1,990 B | **+278%** |
| Base64 + JSON (실제) | 3,900 B | **+641%** |

압축 JSON이 바이너리보다 **4배 가까이 작다.**

이유는 명확하다. deflate는 앞서 본 바이트열을 사전에 넣어두고 재사용한다.
매 메시지마다 똑같이 등장하는 `"playerId"`, `"action"`, `"amount"`가
두 번째 메시지부터는 거의 0비트로 압축된다. 반복이 많을수록 JSON이 유리해진다.

바이너리 포맷에는 그런 학습이 없다. 31바이트는 몇 번을 보내도 31바이트다.

내가 "JSON은 키가 반복돼서 비효율"이라고 지적한 바로 그 성질이,
압축을 켜는 순간 **JSON의 장점**으로 바뀐다.

## 고친 것

**포맷.** 다시 보니 낭비가 있었다.

```
V1: [action 1][amount 8][idLen 4][id N]        고정 13 B
V2: [action 1][idLen  1][id N][amount varint]  고정  2 B
```

`idLen`은 4바이트 `int`였는데 playerId가 255바이트를 넘을 일이 없다.
상위 3바이트가 항상 0이었다. `amount`도 8바이트 `long` 고정인데 실제 베팅액은
대부분 작은 수라 varint로 충분하다. 31 B → 22 B, 절감률 50.8% → 65.1%.

**전송 경로.** SockJS를 쓰지 않는 엔드포인트를 따로 열었다. 바이너리 프레임을
그대로 쓸 수 있어 Base64 팽창이 없다. SockJS 폴백이 필요한 클라이언트는
기존 경로를 그대로 쓴다.

**측정 코드.** 원래 테스트는 이랬다.

```java
@Test
void compareSize() {
    // ... 계산 ...
    System.out.println("JSON 크기: " + jsonBytes.length);
    System.out.printf("용량 감소율: %.2f%%\n", reduction);
}
```

단언이 하나도 없다. 출력만 하고 **항상 통과한다.** 회귀를 잡을 수 없으니
테스트가 아니라 print문이었다. 다음을 검증하도록 다시 썼다.

- 절감률이 id 길이에 의존한다는 것 (짧은 id > 긴 id)
- Base64 래핑이 절감분 대부분을 되돌린다는 것
- 반복 전송에서 압축 JSON이 바이너리보다 작다는 것

마지막 단언이 제일 중요하다. 내 최적화가 지는 조건을 테스트가 명시하고 있다.

## 그래서 바이너리가 틀렸나

아니다. 조건이 있을 뿐이다.

- **단발성·저빈도 메시지**: 바이너리가 유리하다. 압축은 매 메시지마다
  헤더를 붙이고 사전을 새로 만들어야 해서 작은 단발 메시지에는 손해다.
  실제로 63바이트짜리 JSON을 gzip하면 78바이트로 **더 커진다.**
- **고빈도 반복 메시지**: 압축 JSON이 유리하다. 사전이 학습되기 때문이다.
- **CPU가 비싼 환경**: 압축은 매번 CPU를 쓴다. 바이너리는 안 쓴다.

즉 선택 기준은 포맷 자체가 아니라 **메시지 빈도와 전송 계층**이다.
나는 그 질문을 하지 않고 포맷만 봤다.

## 남은 것

세 번의 실수가 다 같은 모양이었다.

1. 한 입력으로 재고 전체라고 했다
2. 함수 리턴값을 재고 네트워크라고 했다
3. 압축 없는 JSON을 재고 실무 기준선이라고 했다

전부 **측정 자체는 정확했고, 측정 대상이 질문과 달랐다.**

그리고 이건 성능 최적화의 기본 함정과 같은 것이다. DB 쿼리가 200ms인데
직렬화 2ms를 1ms로 줄이면 202ms가 201ms가 된다. 숫자는 정확하고 개선도
진짜지만, 병목이 아니었다.

내가 한 건 그 실수의 변형이다. 병목이 아닌 곳을 최적화한 게 아니라,
**병목보다 앞에서 측정했다.** 뒤에 24바이트를 붙이는 단계가 있는 줄 모르고.

> 측정 지점이 병목보다 앞에 있으면, 맞는 숫자도 틀린 결론을 만든다.

숫자가 나왔다고 검증이 끝난 게 아니다. **그 숫자가 사용자에게 도달하는
경로 전체를 재고 있는지**가 남는다. 지금은 무언가를 측정할 때
"이 값과 실제 결과 사이에 내가 안 보고 있는 단계가 있나"를 먼저 묻는다.

README는 고쳤다. 이제 52%가 아니라, 조건별 표와 바이너리가 지는 경우까지
같이 적혀 있다. 숫자는 작아졌는데 훨씬 마음이 편하다.
