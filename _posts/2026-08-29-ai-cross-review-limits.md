구현은 Claude Code로, 검토는 Codex로 나눠서 작업해왔다.
구현에 있어서는 Claude Code가 더 뛰어나다고 느꼈고, 엣지 케이스 발견은
Codex가 더 나은 것 같았다. 무엇보다 서로 다른 AI끼리 교차 검증하는 것이
효과가 좋다는 이야기를 여러 곳에서 봤기 때문이다.

## 검토를 요청하는 방식

검토용 프롬프트는 검토할 AI에게 직접 받았다.
"내 변경사항을 검토하려면 어떤 형식으로 주면 좋겠냐"고 물어서
받은 프롬프트를 그대로 사용했다.

그리고 같은 워킹 트리를 유지한 채로, 변경 내용과 그 프롬프트를 함께 전달했다.
diff만 던지는 것보다 이쪽이 결과가 좋았다. 무엇을 하려던 변경인지에 대한
맥락이 함께 가기 때문이다.

## 효과는 확실했다

Codex의 지적은 거의 다 맞았다. 서로 피드백하는 내용도 정확했다.
같은 모델에게 자기가 짠 코드를 검토시키는 것과는 확실히 달랐다.
모델이 다르면 놓치는 지점도 다르다는 게 실제로 체감됐다.

## 그런데 문제가 반복됐다

그럼에도 고쳐도 고쳐도 다른 문제가 계속 나왔다.

왜 못 잡았느냐고 물어보니 여러 이유가 나왔는데,
결국은 범위가 커서 충분히 검토하기 어려웠다는 쪽으로 모였다.

검증 능력이 아니라 검증 범위가 문제였다.

## 이건 나만 겪는 일이 아니었다

찾아보니 AI 리뷰 도구를 다루는 글들에서 같은 이야기가 나온다.
한 번에 너무 많은 코드를 넣으면 AI 리뷰어가 무너진다. 1,000줄짜리 diff는 컨텍스트 윈도우를 압도하고, 모델은 일관성을 잃고 변경 사이의 연결을 놓치며 스타일 지적 같은 패턴 매칭으로 후퇴한다.같은 리뷰어가 작은 diff에서는 쓸모 있는 피드백을 낸다. 도구가 똑똑해진 게 아니라, 풀 수 있는 문제를 준 것이다.2026년  현재 상위 도구들도 500줄이 넘는 큰 PR을 리뷰할 때 컨텍스트 한계를 겪고, 최고 수준의 도구조차 5~10%의 잘못된 지적을 낸다.거짓 양성을 몇 번 겪은 개발자가 AI 피드백을 아예 무시하게 되는 것이 이런 도구를 포기하는 가장 흔한 이유라고 한다. 





내가 겪은 게 정확히 이 지점이었다.
지적이 틀려서가 아니라, 볼 수 있는 양을 넘겨서 못 본 것이었다.

## 사람 기준 숫자는 이미 나와 있다

코드 리뷰 크기에 대한 연구는 오래전부터 있었다.

결함 발견율은 300줄을 넘어서면서 떨어지기 시작해 500줄 이상에서 크게 하락하고, 리뷰 효율 자체가 90분을 넘기면 저하되기 때문에 한 번에 400줄을 넘기지 않는 것이 가장 효과적이라는 결론이 있다.200줄  미만은 더 빠르게 머지되고 더 꼼꼼하게 리뷰되며, 400줄을 넘으면 리뷰에서 잡히는 버그가 줄어든다.50줄짜리  변경은 250줄짜리보다 약 40% 빠르게 리뷰·머지되고, 되돌려질 확률이 15% 낮으며, 줄당 리뷰 코멘트가 40% 더 많다.한  시간 안에 리뷰를 마칠 확률을 90%로 잡으려면 200줄 정도가 상한이라는 계산도 있다. 





대략 **200~400줄, 리뷰 시간으로는 한 시간 이내**가 기준선인 셈이다.

## AI가 쓰면 오히려 리뷰가 병목이 된다

흥미로운 건 AI 도입 이후의 데이터다.

PR 크기 자체는 크게 늘지 않았다. 2025년 7월부터 2026년 6월까지 중간값이 44줄에서 72줄로 늘었고, 다른 조사에서는 AI 완전 도입 시 추가 줄 수가 74.8줄에서 88.4줄로 18.2% 증가했다. 두 수치 모두 여전히 효과적인 리뷰가 가능한 범위 안에 있다. 

문제는 개수다.
같은 조사에서 PR 처리량은 113% 높아졌다.그리고  AI 에이전트가 만든 PR은 리뷰가 시작되기까지 걸리는 시간이 일반 PR보다 5.3배 길었다. AI 보조 PR도 2.47배 더 오래 대기했다.리뷰어가 완성된 diff만 받고 구현 과정이나 판단 근거는 받지 못하기 때문에, 티켓과 PR 설명과 코드만으로 의도를 재구성해야 한다.게다가 AI가 만든 코드는 대충 읽으면 그럴듯해 보여서 리뷰가 더 쉬워지는 게 아니라 더 어려워진다.PR 대기열이 길어지면 팀은 속도를 유지하려고 엄격함을 낮추고, 실제로 리뷰 없이 머지되는 PR이 31% 늘었다는 데이터도 있다. 







코드를 쓰는 속도는 빨라졌는데 검증 능력은 그대로다.
병목이 작성에서 검증으로 옮겨간 것이다.

## 그래서 범위를 제한하기로 했다

여기서 한 가지를 구분해야 했다.

연관관계로 얽힌 엔티티가 네 개라면, 작업할 때는 당연히 네 개를 다 만들어야
한다. 하나만 만들어서는 컴파일조차 되지 않는다.
**엔티티를 쪼개서 만들라는 뜻이 아니다.**

쪼개는 것은 검증 지점이다.

```
작업: 엔티티 4개를 한 번에 만든다
  ↓
검증 1: 엔티티 + Repository 까지
검증 2: 조회 API
검증 3: 생성/수정 API
```

기반은 한 번에 깔고, 그 위에 쌓이는 기능을 하나씩 끊는다.

## 자르는 기준

**그 자체로 빌드되고 테스트되는 단위여야 한다.**
엔티티 네 개를 두 개씩 나누면 연관관계 때문에 빌드가 되지 않는다.
검증할 수 없는 단위는 자른 의미가 없다.

**목적이 한 문장으로 설명되는 단위여야 한다.**
"Order 엔티티"만 던지면 AI는 형식 검사밖에 못 한다.
"주문 조회 API"라고 하면 이 쿼리로 그게 되는지까지 판단한다.
판단하려면 목적을 알아야 한다.

**한 종류의 판단만 요구해야 한다.**
엔티티 매핑을 확인하는 것과 서비스 로직을 검토하는 것은
집중하는 방식이 다르다. 한 덩어리에 섞이면 뒤로 갈수록 대충 보게 된다.

## 수평이 아니라 수직으로

엔티티별로 묶는 수평 분할보다, 기능별로 묶는 수직 분할이 낫다.

```
수평: Order 전부 → Product 전부 → User 전부
수직: 엔티티 전부 → 조회 API → 생성 API
```

AI에게 시킬 때도 마찬가지다.
"CRUD 전부 만들어줘"라고 하면 엔티티 매핑과 서비스 로직이 한꺼번에 나와서
검토 대상이 섞인다. 엔티티를 먼저 받아 확인하고,
그다음 "이 엔티티로 조회 API 만들어줘"로 넘어가는 편이 낫다.

## 남은 질문

사람 기준으로는 200~400줄이라는 숫자가 있지만,
AI 리뷰어에게 그대로 적용되는지는 확인된 바가 없다.
컨텍스트 윈도우는 사람의 집중력보다 훨씬 크지만,
500줄을 넘으면 품질이 떨어진다는 관찰은 사람 쪽 숫자와 크게 다르지 않다.

일단 200~400줄을 기준으로 잡고 작업하면서,
내 경우에는 어느 지점에서 검증이 무너지는지 측정해볼 생각이다.
